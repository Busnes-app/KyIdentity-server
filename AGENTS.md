# KyIdentity Server

KyIdentity Server is the single-organization SSO provider and central identity authority for the KySecurity Suite of software (KyPost, KyBookmarks, KyNotes, KyPasswords).

## Core Capabilities & Responsibilities

1. **Central User Directory & Replication**: KyIdentity is the source of truth for accounts. When an admin creates, updates, or disables an account, it automatically replicates to paired KySecurity products via bare SCIM 2.0 user bodies signed with `ky-primitives/syncauth`; event type and event ID are part of the signature, and the sync secret is never sent in `Authorization`.
2. **Outbound SCIM 2.0**: Generic `scim` connectors use the target-issued Bearer token encrypted at rest and `ky-primitives/scim` resource writes; known suite types and explicit `suite_webhook` retain signed webhooks. Legacy custom/unknown types pause delivery until an administrator selects a protocol; paused/disabled connectors are excluded from event claims so they cannot starve active targets. Remote IDs and uncertain-create markers persist per connector/local user, surviving local user deletion. Strict bounded externalId lookup recovers lost create responses; unresolved outcomes never trigger another create. Generic deletion uses `active=false` PATCH, preserving downstream data. Writes through stored remote mappings recheck externalId ownership. Configuration review/token replacement requires step-up and atomic success audit; rejected changes record a separate failure audit. Connection tests only prove Users lookup, not write permissions. Setup and limitations: README.md, Outbound provisioning.
3. **OpenID Connect & OAuth 2.0**: Standard authorization-code flow with S256 PKCE required for every client (confidential too; checked at authorize, code creation and exchange), RS256 ID tokens, and JWKS discovery.
4. **Native Device Pairing & Push MFA**: Natively hosts device pairing (`/api/notifications/native/register`) using 90s PIN/QR codes, push challenge dispatch through FCM/APNs relay Workers, direct UnifiedPush, or the UBports push service (Linux) with 2-digit number matching, and TOTP/recovery code support.
5. **Dashboard & Application Launcher**: Suite sidebar layout in Space Grotesk and IBM Plex Mono, themed with Busnes light/dark defaults and the existing KyPost palettes (`web/src/theme.ts`, chosen under Appearance and kept in this browser). Accent is a fill colour only; as text it fails contrast on the light palettes. `css/styles.css` serves the fonts and the pre-bundle fallback page.
   The client table exposes each app's copyable OIDC connection details from the configured issuer, including its client ID, human-readable `username` claim, and compatible credential style; it never displays stored secret hashes. The logout URL it shows is the implemented RP-initiated `end_session_endpoint`.
   Administrators can add non-KySecurity launcher applications and select a built-in icon or an HTTPS site favicon; favicon loading stays in the browser rather than creating a server-side fetch path.
6. **Disaster Recovery & KyBackup (Feature 0)**: `kycap/3` capsules sealed to the suite recovery public key (received at KyRecovery pairing or pinned by hand from the ceremony page), scheduled and on-demand delivery to a local backup directory and to KyRecovery, a schedule set in the admin UI, automated sandboxed live restore drills, and a `restore` command that takes custodian shares from the KyRecovery ceremony (operator runbook: `docs/RESTORE.md`). The recovery public key is not secret, so a capsule that opens proves nothing about its origin: `restore` requires `-expect-digest` (the SHA-256 KyRecovery recorded at deposit, or printed by `export-capsule`), checks it before reading shares and opens a private copy of the checked bytes. `-accept-unauthenticated-capsule` is the only bypass; it warns and the marker/`system.restored` audit records `authenticated: false`. The wire contract is `kyrecovery-server/zero_code_pairing_handoff_spec.md`.

## Security Invariants

- Container-local installer setup is owned by `cmd/kyidentity/setup.go`,
  `cmd/kyidentity/setup_stage.go`, `cmd/kyidentity/setup_export.go` and `internal/store/installer_setup.go`; its bundle and limits are in
  `docs/INSTALLER-SETUP.md`. Use this interface for installer account/client creation.
  Setup ownership, creations and per-change audits commit atomically; existing foreign
  resources and managed drift are refused, and reruns preserve account passwords.
  `--check` uses a read-only SQLite connection with no migrations or reconciliation.
  `apply-setup --stage` takes bounded secret-free metadata on stdin, derives paths under
  `<data>/installer/<setup UUID>/`, and generates owner/everyday passwords, confidential
  client secrets and suite signing secrets on target. Private no-clobber files bind immutable
  intent and credential digests; a native preparation ownership receipt commits with
  its audit before publishing the bundle last. Check writes no preparation/configuration.
  Missing/changed credentials after completion or native application are refused, never
  regenerated, even when filesystem completion markers are lost before account creation.
  Ordinary apply/check verifies preparation receipts for that reserved path.
  `--export-client ID` is a private machine wire, not a setup report: verify the prepared
  receipt and applied native ownership read-only, then export only that exact client's
  OIDC/signing credentials, configured HTTPS issuer, callbacks and native administrator
  binding. Consume its bounded stdout in memory; never log it or persist it on the
  workstation. Other client secrets, passwords and recovery material stay on target.
  SCIM tokens remain destination-issued protected references; the existing encryption key
  is required for connectors and is never created by preparation. Parent symlinks and
  directories writable by other users are refused; sticky ancestors may precede the owned
  protected data anchor. Existing shared/foreign preparation directories are never adopted.
  Each client may declare exact administrator/everyday app roles. Accounts, app access,
  roles, principal mappings, ownership and audits commit together. Management-only clients
  refuse everyday access; undeclared roles, changed holders and policy drift fail inspection.
  These claims do not prove downstream administrator authorization or workflow separation.
  Each client may add one receipt-owned generic SCIM or signed suite-webhook connector, attached atomically to that
  same app identity so provisioning uses its roles and effective access. Tokens are encrypted
  with the existing product key; inspection never generates a key or removes a restore hold.
  Foreign connectors, changed credentials/endpoints and group-delivery drift are refused.
  Connector creation/link audits and initial desired-state work commit with the bundle.
  `suiteWebhook` takes an exact HTTPS endpoint and protected target-local signing secret
  file; protocol, endpoint and credential digest bind its receipt. It never delivers groups.
  Omitting a connector preserves it; changing protocol/credential or a restore hold fails
  check/resume. Existing SCIM receipts retain their original format. Both protocols emit
  the native connector-created audit with the actual type; credentials never enter reports.
  Optional receipt-owned directory groups (at most 32) carry empty initial membership or
  the owned everyday identity, never the dedicated administrator or foreign accounts.
  Client group assignments enable app-scoped group claims; management-only clients refuse
  ordinary groups. Optional SCIM `groups:true` uses native scoped group delivery. Group
  ownership, membership/assignment policy hooks and per-change audits share the setup
  transaction. Inspection/resume refuses changed memberships or foreign group grants
  without overwriting them; native MFA policies remain untouched. Full downstream group
  lifecycle, account migration and suite-wide administrator separation remain gates.

- Public `GET /healthz` uses `ky-primitives/health` with service `kyidentity`, checks database, signing key, encryption key, and audit persistence, and caches the safe `ky.health/1` response for five seconds. `GET /livez` retains dependency-free `{"status":"alive"}`; `/readyz` remains an uncached readiness check and Docker probe.

- `app_registry` gives each OAuth client, launcher card, and paired system a stable application identity. Startup backfills separate records without guessing links; insert/delete triggers keep references complete across all creation/deletion paths. Admin linking/unlinking requires step-up, matching revisions, non-overlapping connection types, and an atomic audit with readable connection names. Linking preserves connection IDs and credentials, and requires equal access and authentication settings with no assignments on either record; unlinking copies access and authentication settings and grants. Existing apps migrate to explicit all-active-user access, while new apps default to assigned-only. Direct and group grants combine by union; global admins do not bypass assignments. The same SQL access rules drive admin previews, launcher filtering and OAuth issuance. Access loss deletes pending and spent authorization codes and revokes affected tokens in the mutation transaction; token registration checks the originating code, active session and current access atomically. A re-grant never revives a deleted code or revoked token. Every access mutation also reconciles provisioning desired state in the same transaction.

- Directory groups have stable IDs and unique names; names reject invisible format/control characters, private-use characters, and non-ASCII whitespace. Membership/deletion audit records capture readable target identifiers in the mutation transaction; explicit membership never grants global administrator status. Admin group/member lists are searched and paginated. Every group or membership mutation requires operation-bound step-up and commits with its audit record; individual membership writes are idempotent and preserve concurrent edits. Foreign-key cascades remove memberships when a user or group is deleted. Membership removal and group deletion atomically revoke app access only when no alternative grant remains. Groups assigned to a generic SCIM connector with group delivery enabled are replaced wholesale at the target; members are limited to in-scope users the target already holds.

- Organization, administrator and group MFA enrollment policies intersect permitted factors and use the earliest persisted per-user scope deadline. Login, longer grace, policy reactivation and membership removal/re-addition never extend deadlines. Restricted sessions only access identity/factor enrollment and logout, never apps, admin mutations, OAuth issuance or online tokens; enrollment requires a fresh permitted MFA login to exit a persisted restricted session. Recovery is restricted whenever MFA is required. Policy writes require step-up, matching revision and recent actual compliant administrator login, and atomically invalidate OAuth grants with audit. Policy previews and rejected writes record separate audit events with bounded rejection reasons; preview responses fail closed if their audit cannot persist. Password-only enrollment fallback is available only when no factor of any method is enrolled; an existing factor outside the allowed policy mask must still be verified. Device pairing-token issuance consumes an operation-bound step-up grant, including restricted enrollment sessions; the UI validates its ISO expiry timestamp before displaying the countdown. Last-compliant-factor removal is rejected under the mutation writer lock; admin reset ends grace. Group membership changes for required policies reject empty factor intersections and require a compliant administrator session, then invalidate affected OAuth interactions/codes/tokens atomically with their audit. Idempotent membership writes preserve existing grants. Group deletion of a required-policy group checks recent compliant administrator login under the writer lock and invalidates affected grants before cascading its policy and deadlines; new groups default to no MFA requirement. Role promotion rejects incompatible masks. Policy audit includes the readable group name; rejected policy audit targets retain only existing policy identities. Session policy lookups constrain membership and policy queries to the session user, with a 3,000-user query-plan regression check. `internal/store/enrollment_policy_test.go`, `internal/store/group_enrollment_test.go` and the enrollment API tests cover deadline persistence, PR06a migration, membership conflicts/token races, recovery and real enrollment-to-login flows.

- Generated key files (secret, encryption, RSA signing, VAPID) are created only through `crypto.CreateKeyFile`: fsynced temp file, hard link, never replaced. A loser of a concurrent first start gets `fs.ErrExist` and re-reads the winner's key (`TestLoadOrCreateRSAKeyConcurrentFirstStartAgrees`, `TestKeyFileConcurrentFirstStartAgrees`).
- `bootstrap-admin` reads the password from stdin only (`-password` refused), honours a validated bare `-email`, and creates the administrator with its `admin.user_created` audit row in one transaction (`ensureBootstrapAdmin`, shared with first start). An existing name that is not an active administrator is an error; first start writes `first-run-password.txt` only for an account it created.
- Public deployments require an HTTPS issuer and secure session cookies; loopback HTTP is development-only.
- `KYIDENTITY_LISTEN_HOST` optionally pins the HTTP listener to a literal IPv4/IPv6 address,
  combined with `KYIDENTITY_PORT`. Empty retains all-interface container binding. Host-network
  fixtures set `127.0.0.1`; invalid hostnames, ports and scoped addresses fail configuration.
  This changes socket binding only, never issuer identity or proxy trust.
- Outbound delivery is FIFO per connector/local user. Only unsent claim leases expire automatically; persisted delivery attempts fence uncertain remote mutations across restart, timeout and local user deletion. Acknowledgment and event/system status commit together. Mutation body replay inside the HTTP transport is disabled so lost responses reach the persisted fence. Generic and suite synchronous writes require completion responses; once a mutation's headers are written (`httptrace` `WroteHeaders`), 202, 408, server errors other than 503 and lost responses remain blocked. A request that never wrote its headers (DNS, refused or netguard-refused dial, TLS) and 429/503 refusals back off without a fence; a shutdown before the write spends no attempt. One pass delivers connectors concurrently (at most `dispatchConcurrency`) and each connector's claimed events in claim order; a claim holds one event per connector/user. Suite sync exposes bounded attempt listing and read-back diagnostics, which never automatically clear a fence. Read-back probes record success/failure audits with local target identifiers only; rejected recovery writes record separate failure audits with fixed reasons, including after step-up consumption. Recovery requires operation-bound step-up, the exact expired attempt, operator-confirmed worker/remote quiescence and an atomic audit. Clearing an uncertain-create guard additionally requires explicit no-create confirmation and empty externalId read-back. Bulk resume (`POST /api/admin/systems/{id}/deliveries/resume`) applies the same step-up and quiescence confirmation to every expired attempt of one connector with one atomic audit listing the released tokens; it refuses `allowCreateRetry` and never clears an uncertain-create guard. Upgrade requires stopping old workers and settling their remote operations. `sync_resource_state` records each connector/resource's desired state, whether the receiver acknowledged it, and a monotonic revision carried on every event (suite `meta.version`). Desired state derives from `effective_app_access`; the migration backfills current pairs as provisioned. Queuing a new desired state deletes unfenced queued work for the resource and never touches a fenced attempt; a never-acknowledged resource that loses scope is dropped, never disabled. Inactive states never create accounts at generic SCIM targets. Exhausted unfenced events of an existing connector re-enter backoff on every reconcile only while their revision is current, otherwise they are discarded; deleting a connector deletes its events with it (its attempts go by trigger) and startup drops events whose connector is gone; deletion fans out to every enabled connector with the profile limited to connectors that held the account. Group delivery is a per-connector flag limited to generic SCIM that a connection review changes only when the request names it; group writes re-verify the stored mapping by externalId and require 200/204; read-back follows the attempt's collection. Reconciliation jobs (`sync_reconcile_jobs`) run one per connector under a lease with a bounded re-claim budget; they list the target page by page and treat any failed page, changed total, short page, duplicate ID or oversized collection as incomplete, recording observations but never inferring absence or deactivation. Only resources whose externalId names a user with effective access to that connector, held state or a stored mapping are compared; unrelated remote accounts are never touched and a target cannot manufacture holder status. Preview writes only observations; repair writes mappings, treats a disputed mapping as a counted conflict it never writes through, queues only desired-state work through the same supersession path as delivery, requires step-up, lists afresh rather than applying a stored preview, and is audited when queued (including by schedule) and when finished with its counts. Listings run on a separate goroutine with a per-collection time and page budget so delivery is never delayed by a target. Suite webhooks record `unsupported` observations. Per-user rows separate desired, queued, acknowledged and observed state. `internal/store/sync_delivery_test.go`, `internal/store/provisioning_test.go`, `internal/sync/delivery_test.go`, `internal/sync/provisioning_test.go` and the recovery API tests cover stale claims, restart, deletion races, real delayed HTTP responses, audit rollback, recovery gates, grant transitions, supersession behind fences, scoped resync, group lifecycle and concurrent/restart ordering.

- `Store.rdb` is a `query_only` pool on the same file for read-only snapshot transactions (`ListGroups`, `ListAppAccessGroups`, `GetUpstreamGroup`, `ListUpstreamGroups`, `ListProvisioningState`), so they never take the IMMEDIATE write lock of `Store.db`. Anything that writes uses `db`. A `:memory:` store shares one pool.
- Account creation and updates write their replication outbox events in the same database transaction. The final active administrator cannot be deleted, disabled, or demoted.
- Sensitive API and OAuth responses are `no-store`; registered redirect and launcher URLs must be HTTPS, except loopback HTTP for development.
- Legacy device-pairing tables containing plaintext PINs are rebuilt on startup; their 90-second tokens are intentionally invalidated.
- MFA reset invalidates pending native-device pairing tokens; native registration consumes a live token in the same transaction that creates the approver and push method.
- PIN pairing (`MatchDevicePairingPIN`) looks up and counts in one immediate transaction: each miss increments `pin_failures` on all the user's live tokens, and the miss reaching `PairingPINBudget` (5) expires them all, QR tokens included.
- IP rate-limit buckets key on `rateLimitIP`/`rateLimitPrefix`: IPv6 collapses to its /64, IPv4 and IPv4-mapped stay whole. `ClientIP` stays exact for audit; never key a limiter on it directly.
- The limiter map is swept by a ticker `Server.Start` owns (not on the request path). At `maxLimiters` a new key replaces a fully refilled bucket found within `limiterEvictionProbe` entries, else is refused; live buckets are never evicted.
- The `mfa_methods` push row follows `enrolled_factors` bit 2: `changeEnrollmentDevice` (`syncPushMethodTx`) deletes it when no approver device with a key remains and restores it when one returns, in the device write's transaction.
- Relay keys: `/send` 401 with `code: key_superseded` (a key `/register` displaced) makes `RelaySender` re-register once under a per-endpoint mutex, atomically replace the key file, and retry; a plain 401 or an operator-supplied key never re-registers.
- Device sign-on: `POST /api/user/devices/pairing-token` accepts `{signOn}` (default false, echoed; the web UI always sends it); the flag lands on the registered device as `can_sign_on`. `PUT /api/notifications/native/devices/{id}/sign-on` (session + owner + operation-bound step-up, `{canSignOn}`, audited `device.sign_on_changed`) toggles it; `DELETE /api/user/devices/{id}` and `PUT .../{id}/mfa` (`device.mfa_approver_changed`) also spend step-up, commit their success audit with the change, and answer 404 when no device of the caller's matched; the web device list exposes the toggle, and the Phones section shows the pairing checkbox above the device list. Enabling needs `is_mfa_approver` (409 `device_not_approver` otherwise); disabling is always allowed.
- `POST /oauth/token` `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`: ES256 assertion signed by a native device's enrolled key (`kid` = device id, `iss` = `device:<id>`, `aud` = `<issuer>/oauth/token`, `client_id` bound, window <=300 s, single-use `jti` in `device_signon_jtis`, required `origin`, matched per origin (scheme, host, port) against the client's registered redirect URIs, so relays sharing an origin are one trust domain; each consumer accepts only its own base-URL origin, so extra registered aliases do not widen it). Issues access + ID token with `signon_method: device`, `device_id`, `origin`, `auth_time` and the authentication evidence = the assertion `iat` (when the phone signed, clamped to now), and `amr`/`acr` by attestation grade (see Attestation); no refresh token; audited `device.signon`.
  - Requires BOTH `can_sign_on` and `is_mfa_approver`. `ResetUserMFA` and `DeleteUserMFAMethods` clear `can_sign_on`, so an admin MFA reset ends device sign-on.
  - Enforces the client's authentication policy as the code grant does (`Valid`, `EvidenceReason`, `Deadline` cap). Unattested (`none`) devices are single factor and additionally refuse `fresh`/`max_age` modes (no recently entered password): only `reuse` + `password` admits them.
  - Policy refusals (app policy, enrollment guard, app access) wrap `ErrDeviceSignOnNotPermitted` and answer `invalid_grant` with `error_description: signon_not_permitted`. Like `device_signon_disabled` they occur only after signature verification; pre-signature failures stay generic.
  - Unattested (`none`) and `appattest`: `amr: [pop]`, `acr: urn:kysignon:acr:device`, `PrimaryAuthenticatedAt` = assertion `iat` (clamped to now), no `FactorAuthenticatedAt`, empty `FactorMethod`. `mfa_session_access` refuses users whose enrollment policy requires MFA (`RecordIssuedToken` -> `ErrAppAccessDenied` -> `invalid_grant`), and app policies with `Factor` other than `password` refuse. Enrollment grace admits it only while the user has no enrolled factor in the policy's allowed methods, so never when push is allowed.
  - Attestation (`internal/attest`): native registration accepts `attestation`, a JSON array of base64 DER certificates, leaf first (body cap 64 KiB). Verified against Google's roots (embedded `roots.json`, refreshed daily from `https://android.googleapis.com/attestation/root`, plus PEM in `KYIDENTITY_ATTESTATION_EXTRA_ROOTS`), the revocation status list (`KYIDENTITY_ATTESTATION_STATUS_URL`, default Google's, empty disables with a startup warning; a list older than 3x its max-age is unknown and new pairings grade `none`), the challenge `SHA-256("kyidentity-attest-v1|" + credential)` (credential = pairing token or `userId|pinCode`), a hardware-enforced per-use policy (userAuthType present, no authTimeout, no noAuthRequired, origin generated, EC P-256 signing), and KyAuth's package `org.kysecurity.authenticator` with a signing digest in `KYIDENTITY_KYAUTH_CERT_SHA256` (comma-separated). Grades `none|tee|strongbox` (and iOS `appattest`, below) land in `attested_level` with `attested_at`, `boot_state` (`locked-verified|locked-selfsigned|unlocked|unknown`) and `attestation_serials`, graded before the enrolment write and stored in the same upsert as the key it graded, so a re-pair carries only its own grade. Pairing never fails because of attestation; `device.registered` audit details carry `attestedLevel`, `bootState`, `attestationReason`.
  - iOS App Attest (`internal/appattest`, contract `KyAuth-iOS/docs/specs/2026-10-11-ios-app-attest.md`): registration field `appAttest {keyId, attestation}` is graded only for platform `ios`, and the Android chain only for `android`. Steps: CBOR (`fxamacker/cbor`, duplicate keys refused, 16 KiB cap) `fmt apple-appattest`; `x5c` chains at the current time to the embedded Apple App Attestation Root CA, pinned by SHA-256 in code and test; leaf extension `1.2.840.113635.100.8.2` nonce = `SHA256(authData || SHA256("kyidentity-appattest-v1|" + credential + "|" + publicKey))` (`AppAttestClientData`); `keyId` = SHA-256 of the leaf's uncompressed point = `credentialId`; `rpIdHash` in `KYIDENTITY_APPATTEST_APP_IDS` (empty disables); sign count 0; AAGUID production, or development only with `KYIDENTITY_APPATTEST_ALLOW_DEVELOPMENT=true`. Pass: `appattest`, boot state `unknown`, no serials. Failure: `none`, typed `appattest.Reason` in the log and the audit `attestationReason`, never in the response. App Attest proves the app, not that the key is in the Secure Enclave or needs user presence, so `appattest` earns no second factor. Tests use `internal/appattest/appattesttest`, a generated CA; no real Apple object has been verified yet.
  - Only Keystore-attested (`tee`/`strongbox`) devices earn MFA grade: factor evidence `FactorMethod push`, every policy mode evaluated as for the code grant, `amr: [hwk, user, mfa]`, `acr: urn:kysignon:acr:mfa`, claim `attested: tee|strongbox`. Org MFA method masks still apply (an org that disallows push refuses attested devices). `DeviceBinding` includes `attested_level`, so a downgrade mid-exchange refuses (`device_signon_disabled`).
  - Admin setting `attestation.requireLockedBootloader` (`GET/PUT /api/admin/attestation/settings`, PUT step-up, audit `admin.attestation_configured`), default off. The boot state is recorded either way. Enforced at pairing (fails closed if the setting is unreadable) and by the daily housekeeping sweep (skips the bootloader check if the setting is unreadable).
  - Housekeeping (every 15 min) refreshes roots and the status list whenever the list is stale, so a failed fetch retries next tick; fetches refuse redirects, and a fetched root outside the embedded/extra set is logged with its subject and SHA-256. The daily sweep downgrades devices with revoked serials (and unlocked boot states when the setting is on), only while they still hold the key it read, audit `device.attestation_downgraded`; it skips `appattest` devices. An unknown status list never downgrades.
  - Unverified on hardware: No real-hardware pairing has been observed; the positive path is unproven until a physical phone pairs against this verifier. Emulators always grade `none`. The checks that close this are numbered in `docs/attestation-verification-plan.md`.
  - The `can_sign_on` check runs after signature verification, so `device_signon_disabled` only ever reaches the key holder.
  - Origin binding: the relay names `client_id`, so the assertion's `origin` (bare `https://host[:port]`, <=256 chars, canonicalised by `canonicalOrigin`: lowercase host, `:443` dropped) must exactly equal the origin of one of the client's registered redirect URIs (`registeredOrigin`, same canonicalisation; non-https URIs never match). Checked after the signature and `can_sign_on` checks; a mismatch is `errAssertionOrigin`, the generic `invalid_grant`, audited with the presented origin. Every consumer server's public origin must be registered on its client; its browser SSO redirect URI already does this.
  - Never checks `client_secret`: the assertion is the client authentication.
  - Rate limit: `device_signon` bucket, 10 burst, 0.2/s per IP, inside the route's `oauth_token` limiter.
  - Revocation does not reach consumers: turning sign-on off or deleting the device does not end live device login sessions, and expired device sessions are swept without a back-channel logout. Consumer servers must not rely on back-channel logout to revoke credentials minted from a device sign-on; they expire on the consumer's own schedule (access token <=15 min).
  - Like the code grant, the token is bound to the policy it was evaluated against: `ClientAuthenticationPolicyBinding` returns the app's `auth_revision`/`role_revision`, and `RecordIssuedToken` inserts only if the `app_registry` row still holds them, in the same statement. A policy or role edit landing mid-exchange refuses the token (`invalid_grant`) and deletes the device session. The same INSERT rechecks device eligibility (`IssuedToken.Device`: same id, owner and `public_key`, `can_sign_on` and `is_mfa_approver`), so an MFA reset, sign-on toggle, device delete or re-pairing mid-exchange refuses the token; the engine re-reads the device and answers `device_signon_disabled`, and the device session is deleted.
- Native push relay URLs must be HTTPS; relay API keys are runtime secrets loaded from env or generated under the data directory, never committed.
- Push approvals are `kyidentity-push-v2` messages binding issuer origin (from `KYIDENTITY_ISSUER_URL`, startup fails without one), user, device, challenge, purpose (`login`|`step_up`) and expiry. The respond request names its `deviceId` and only that device's key is tried; failures stay generic. v1 is not accepted. Format and vectors: `design.md`.
- Push target refreshes are `kyidentity-push-token-v2` messages (`PushTokenRefreshMessage`: origin, device, issuedAt, transport, token SHA-256, p256dh, auth), authenticated by the enrolled device P-256 key, bound to the configured issuer and a fresh monotonic timestamp, and atomically persisted (all four push fields) with their audit event; push tokens are never credentials. v1 is not accepted. Vectors: `internal/mfa/push_target_test.go`.
- `native_devices.push_transport` is `fcm` (relay), `unifiedpush` or `ubuntupush`; `platform` is `android`, `ios`, `macos` or `linux`. Widening either SQL CHECK needs `migrateNativeDeviceCHECKs` (copy out and recreate under the same name, never RENAME: `enrolled_factors` reads the table; foreign keys off on that one connection so legacy orphan rows copy exactly, and back on before it is pooled). `ValidatePushTarget` is the one check for registration and refresh: UnifiedPush endpoints pass `netguard.ValidateDeviceURL` (HTTPS, public addresses only, `AllowPrivate` ignored); ubuntupush tokens are 1-512 bytes of `[A-Za-z0-9+/=_.:-]`; both need p256dh (on-curve uncompressed P-256 point) and auth (16 bytes); fcm carries no keys. `PlatformAllowsTransport` (registration and refresh) refuses fcm for linux and ubuntupush for anything else. `UbuntuPushSender` posts the same challenge JSON, RFC 8291 sealed by `sealAES128GCM` (pinned to the RFC 8291 example) into one 2048-byte record, to `KYIDENTITY_UBUNTU_PUSH_URL` (https, default push.ubports.com) as `KYIDENTITY_UBUNTU_PUSH_APPID` with `replace_tag` `kyauth-mfa` (a newer request replaces a pending one) and fixed notification text; serialized `data` must stay within 4096 bytes; `unknown-token` (400) clears the target, any other non-2xx is a failure. `UnifiedPushSender` sends RFC 8291 only, through `netguard.DeviceClient`, VAPID key at `<DataDir>/push-vapid-private.key`; there is no plaintext path. The key file is created by `crypto.CreateKeyFile` (never overwritten) and refused if group/other can read it. Records are padded to 2 KiB. Devices are sent to concurrently. 404/410 clear the target only if endpoint and keys are still the ones sent to. `netguard` refuses loopback, link-local, metadata, NAT64 and the other reserved ranges always; `KYIDENTITY_ALLOW_PRIVATE_CALLBACKS` (default off) opens only RFC 1918/ULA/CGNAT, and only for operator-supplied URLs. Device-supplied URLs use the `Device` variants. `AllowLoopback` is a test hook no configuration sets. Logs name device and transport, never endpoints or keys.
- Login lockout: every rejected login second factor (TOTP, recovery, passkey) calls `RecordFailedLogin`; `resolveMFAToken` refuses locked accounts; `ClearFailedLogins` runs only in `createSessionAndRespond`. Verifiers spend a token attempt with `ReserveMFAAttempt` (single conditional UPDATE) before checking proof. Recovery verify has its own `mfa_recovery` limiter. Argon2id runs through `auth.idKey`, capped at 8 concurrent calls; `auth.ErrBusy` (also from `DummyVerify`) must reach `argonBusy` (503 + `Retry-After`) before any wrong-password handling. Before the password is proven, locked, inactive and unknown accounts and a mismatched authorization interaction answer exactly as a wrong password (401 `invalid_credentials`, same `DummyVerify` cost; the interaction is checked only after the password); audit reasons stay distinct. The post-password second-factor lock keeps `429 account_locked`: that caller already proved the password. `internal/api/login_lockout_test.go` covers these.
- Login push fatigue: `CreatePushChallenge(…, "login")` inserts only while the user has no live login push (`CreateLoginPushChallenge`, one conditional INSERT), else `ErrPushPending`; a shared challenge would let one approval sign in two password holders, so it is never reused. `loginPush` also caps sends at `loginPushesPerHour` per user (`login_push:<id>` limiter) and records the outcome as `push` in `auth.mfa_challenge`. `pushFatigueThreshold` denied/expired login pushes in an hour (`CountUnansweredLoginPushes`; housekeeping keeps challenges an hour past expiry) audit `auth.mfa_push_fatigue`, checked before each send and on each denial.
- Recovery codes are stored as `hmac:` + HMAC-SHA256(`DeriveKey(key, "kyidentity:recovery-code")`, `userID|code`). Legacy bare SHA-256 rows cannot be converted; `ConsumeRecoveryCode` still matches them in the same single UPDATE until the user regenerates, and `/api/auth/me` returns `recoveryCodesNeedRegeneration` while one is unused.
- Step-up requires password plus an enrolled TOTP, push, or passkey when any factor is enrolled. Grants and pending challenges bind to user, session, and exact method/path (enrollment preparation maps to its final mutation). Recovery grants only directly authorize replacement TOTP/passkey enrollment; TOTP enrollment still rotates recovery codes and a recovered factor can authorize later operations. Challenge issuance and completion each commit with their audit event; lockout and missing-factor denials are audited. Cancellation burns pending challenges and raced grants. Step-up does not rewrite login authentication evidence.
- Every modal, step-up included, is the shared `Modal` (native `<dialog>` via `showModal()`): the top layer stacks a grant request above the dialog that opened it, so it can never be painted under its caller and silently cancel the action it protects. `stepUpStacking.test.ts` refuses hand-rolled `modal-backdrop` markup.
- A client secret is shown once and rotated in place from the clients table; rotation revokes that client's outstanding tokens, so delete-and-recreate is never the recovery path for a lost secret.
- Sessions have both a configurable absolute lifetime (24h default) and inactivity lifetime (30m default); both are enforced in the store lookup.
- Login sessions record actual password and second-factor verification times. Authorization codes snapshot that evidence; ID-token `auth_time` is the password proof time, never code creation. Legacy sessions omit unknown authentication claims. Recovery is identified separately from ordinary MFA; claim values are documented in README.md.
- OIDC `prompt=login` and `max_age=0` require one fresh login per authorization interaction; positive ages persist an absolute proof deadline checked atomically at token registration. `prompt=none` never creates UI. Supported requested assurance is password or ordinary MFA; recovery cannot satisfy MFA. Validated requests are stored in bounded five-minute interactions, bound to a signed HttpOnly browser cookie, the original account/session when present, and the exact resulting login session. Session creation and interaction satisfaction commit together; code creation consumes the interaction in its transaction. Cancellation and code issuance serialize, with the first committed operation winning. A completed password/MFA proof still creates an unbound active-user session if its interaction expired or was cancelled, with an explicit authorization-restart signal; it cannot resume that request. Interactions are capped at ten per browser and per account, including ownership assigned on anonymous login completion. Upgrade/capacity recovery trims pre-limit account overages, preferring completed proofs; ordinary capacity pressure evicts anonymous unfinished interactions. Authorize charges an IP limit for every request; browser identities never allocate shared rate-limit buckets. It returns protocol errors only after validating the callback. Per-app authentication policy supports reuse, bounded password age or a fresh interaction every authorization, with independent ordinary-MFA/passkey age. Client requests only strengthen it. Policy edits require step-up and matching app revisions; the audit, incremented policy revision, interaction/code invalidation and client token revocation commit together. Code creation rechecks policy under the writer lock; registration checks the same app identity/revision and earliest proof deadline. Recovery and weaker factors cannot satisfy a passkey policy. Legacy ordinary SSO remains compatible; first upgrade invalidates old pending codes/interactions.

- New authorization codes and access-token records bind to their originating session. Token registration requires that session and an active user in the same SQL statement; removing the session blocks code exchange and online use of its tokens. Upgrade invalidates legacy pending codes and MFA flows, preserving existing sessions and already-issued tokens without inventing evidence.
- RP-initiated logout at `/oauth/logout` ends only the current browser session, and silently only when the `id_token_hint` verifies against this issuer's key, names this client and its `sid` resolves to the current session of the signed-in subject; a hint for another user or another login of the same user gets the confirmation page with a session-bound token instead. `post_logout_redirect_uri` must byte-match a registered post-logout URI or the request fails without redirecting. ID-token `sid` values are minted per client and session in `oidc_client_sessions` and cascade with the session; they never equal internal session IDs. Expired hints identify a login; forged, foreign-issuer or access tokens do not. The endpoint bypasses double-submit CSRF only so its same-site confirmation form can carry the session-bound CSRF HMAC in a `confirm` field; a cookieless (cross-site) POST is bounced with a 303 to the equivalent top-level GET and never reported as a sign-out.
- Back-channel logout: every path that ends a session (`revokeSessionsTx`) or one client's access queues a `logout_deliveries` row per client that saw the login and registered a receiver, in the same transaction, before the session row and its cascading `sid` mapping are deleted. The worker leases a row, mints a fresh `logout+jwt` token per attempt (`events`, `sid`, `sub`, two-minute `exp`, no `nonce`/`token_use`), POSTs it through the netguard client without following redirects, and records the outcome under its claim token; five failed attempts mark it failed and only an audited administrator retry resets the budget. Receiver URIs pass `netguard.ValidateURL`. Logout tokens are never accepted as ID token hints or access tokens. Claims are exclusive per client across four workers so one dead receiver cannot stall the rest; delivered rows are pruned by housekeeping after seven days while failed rows stay (absence must never read as success); transport errors are shown to administrators only; session expiry never queues a delivery, and no raw `DELETE FROM sessions` outside `revokeSessionsTx` may end a login.
- KyPost recovery evidence: `POST /api/admin/systems/{id}/recovery-evidence` is `permAdmin` plus operation-bound step-up. Read [docs/KYPOST_RECOVERY_EVIDENCE.md](docs/KYPOST_RECOVERY_EVIDENCE.md) before changing it. One immediate store transaction reads current app scope/roles and retained user revisions, locally signs with the active unheld KyPost pairing credential, and commits the audit before publishing exact JSON and syncauth headers. Bounded exact-set challenges, explicit minimal inactive entries and nullable unknown revisions are mandatory. The export changes no hold, queue or revision; no consumer/release path is shipped. `internal/store/recovery_evidence_test.go` and `internal/api/recovery_evidence_test.go` cover authority, disclosure, audit, signature and concurrency boundaries.
- Offboarding: `offboardUserTx` is the one lifecycle operation for disable and delete. It revokes local access and records an inactive desired state for every connector holding the account (tracked state row or non-empty `scim_user_links` mapping); deletion runs it with `user.deleted` before removing the user row, and never deletes `sync_resource_state` or `scim_user_links`. `UserOffboarding` reads completion for deleted users too: the acknowledgement is `sync_resource_state.offboarded_at` (stamped by `provisionedTx` on a delivered inactive/deleted event for the current revision, cleared by any newer desired state), never inferred from prunable outbox rows; `verified` requires a listing at or after that acknowledgement and is never true for `unsupported`; a listing that still sees the account active contradicts the acknowledgement.
- Onboarding: a user created without a password is `pending` and `disabled` with an empty `password_hash` (which never verifies); every `status='active'` guard therefore keeps it out of sign-in, sessions, provisioning and app access. `account_tokens` holds only hashes; `IssueAccountToken` retires earlier links of the same kind and requires pending for activation, active for reset; `RedeemAccountToken` re-asserts the issuance predicate (pending for activation, active and not pending for reset), spends the token, sets the password, activates, verifies the address only for `delivery='email'`, revokes all access (which retires every remaining link; `revokeUserAccessTx` expires `account_tokens`) and clears lockout in one transaction. `ChangePassword` keeps the proving session and revokes the rest. An email change clears `email_verified_at` and expires outstanding links. Raw links never enter audit details. Mail settings live encrypted in `system_settings`; `mail.Settings.Send` refuses non-TLS transports and CRLF in recipient or subject, and uses the bare address for the envelope; `mail.Save` keeps a stored password only for an unchanged relay. `Forgot` answers before contacting the relay.
- Row secrets (TOTP, connector credentials, mail settings) use `crypto.Seal`/`Open` only: AES-256-GCM under `DeriveKey(master, "kyidentity:seal:"+purpose)` with AAD `purpose|row`, output `v2:`+base64 (`:` cannot start legacy base64). Purposes and row identities are in `internal/store/sealed.go`: `mfa_totp|<user_id>` (the upsert keeps the old method ID, so it cannot be bound), `paired_system|<system id>` (assign the ID before sealing), `mail_settings|mail_settings_enc`. `Open` refuses legacy ciphertext. `SealLegacySecrets` runs at server start before anything reads a secret: one transaction re-seals every legacy row and writes `sealed_secrets_version`; once that marker exists legacy rows are never migrated again, so a planted legacy blob stays refused. A legacy row that does not decrypt aborts start with its table and row named. `apply-setup` does not migrate. A new sealed column must be added to `sealedColumns` and the drill.
- Inbound SCIM: `scim_connectors` + `scim_connector_tokens` (hash only, scope, last use, revoked_at); `AuthenticateSCIMToken` requires a live token on an active connector. Owned users carry `source_connector_id` + immutable `external_id` (unique per connector), `source_active` and `locally_disabled`; `User.ApplySourceState` derives status (active only if source active, no local override, not pending). `CreateUpstreamUser` always creates a pending, passwordless, role=user account and maps any UNIQUE clash to `ErrUserConflict`; `IssueAccountToken` refuses activation for an owned account that is upstream-inactive or locally disabled, and `RedeemAccountToken` derives activation status from the source state in SQL rather than writing `active`; `UpdateUpstreamUser` runs inside the single `updateUser` transaction (row read under the write lock, caller `prepare` before any write; callers without `prepare` get the source fields and, for source-owned rows, username/display name/email folded from the row and status re-derived, so a stale admin copy never undoes an upstream write), keeps role, override, password and pending local, refuses external id changes, and `rejectCrossIdentityTx` blocks a username or email that another account uses as either. Disconnect-with-disable enforces `ErrLastActiveAdmin`. `/scim/v2/` bypasses CSRF and ignores cookies; connector tokens never reach the admin API. Admin edits of source-owned name/email are refused (`source_owned`); a local status change sets/clears `locally_disabled`. Disconnecting needs an explicit keep/disable choice and clears the source fields on users and groups. Groups: `directory_groups.source_connector_id`/`external_id`; `CreateUpstreamGroup`/`ReplaceUpstreamGroup`/`DeleteUpstreamGroup` run inside one transaction over `setGroupMembershipTx`/`deleteGroupTx` (the shared bodies of the admin paths), `membersOwnedTx` refuses any member that is not a user of the same connector, PATCH is computed then applied as one replace, and `UpdateGroup` refuses a local rename of a source-owned group (`ErrGroupSourceOwned`). Upstream changes to a group with a required MFA policy fail closed (`ErrEmergencyAdministrator`, no session).
- App roles: `app_roles` + `app_role_user_assignments`/`app_role_group_assignments` per `app_registry` row; `UserAppClaims` resolves roles (direct or via group) and, when `groups_claim` is on, the app's assigned or role-mapped groups; `identityClaims` in the OAuth engine builds ID-token and UserInfo claims from the same granted scope (`profile`, `email`) and fails with `ErrClaimsTooLarge` above `MaxIdentityClaimBytes`. `roleChangeTx` bumps `app_registry.role_revision`, revokes the affected users' tokens and codes for the app's client and re-queues their SCIM profile via `scimUserPayloadTx` (app roles replace the global role for a connection whose app defines roles); `authorization_codes.role_revision` is stamped at issue and checked in `RecordIssuedToken`. `legacy_role_claim` is on only for apps that predate roles; `knownScopes` refuses unknown client scopes; administrator linking/unlinking refuses apps with roles.
- Audit search: `AuditFilter` (actor id-or-username, target id, target type, action prefix via escaped LIKE, outcome, from inclusive/to exclusive) with `SearchAuditEvents` (total order `created_at DESC, id DESC`, indexes `idx_audit_events_{created_id,action,actor,target}` from `migrateAuditIndexes`; `TestAuditFiltersAndIndexes` checks `EXPLAIN QUERY PLAN` at 6,000 rows) and `StreamAuditEvents` (same order, row bound, stops when the sink errors). `ExportAuditEvents` streams CSV or JSONL under `permRead` and a per-IP limiter, bounded by `auditExportMaxRows` and `auditExportTimeout` (package variables; the deadline context reaches the SQL through `SearchAuditEventsContext`/`StreamAuditEvents(ctx, …)`), redacts details with `RedactAuditDetails`, neutralises formula cells with `csvCell`, records `admin.audit_export_started` before the first byte (refusing the export if that fails) and `admin.audit_exported` with the outcome afterwards, folds the CSV writer's own error into the outcome, and appends an in-band `_export: incomplete` marker (reason limit, timeout or error) whenever the file is short of the filtered set. `DeleteAuditEventsOlderThan` remains the only retention path.
- Alerts: `internal/store/alerts.go` derives alerts from audit rows queued by the `audit_events_alert_queue` trigger (`alert_queue`, cascades with retention) and from connector state, in `EvaluateAlerts` (one transaction per batch: classify, `raiseAlertTx`, drain the queue; then `evaluateOutages` for `paired_systems.status='failing'`/failed outbox rows and failed `logout_deliveries`, resolving when clear). One live alert per rule and key (`alerts_live` partial unique index); a repeat on an open alert counts, on an acknowledged one reopens and re-mails; outages never bump or reopen. Rules: `privilege_change` (`admin.user_created` role admin, `admin.user_updated` with `roleChanged`, `admin.delegations_updated`), `recovery_use` (`auth.mfa_recovery_consumed`, `admin.user_mfa_reset`, `auth.password_reset`), `connector_credentials` (`admin.scim_token_issued/revoked`, `admin.system_created`, `admin.system_configured` with `credentialRotated`, `admin.mail_configured`), `login_failures` (non-success `auth.login` counted per known account id or, for unknown names, per source address within `AlertSettings`; the submitted name is never a key, and past `loginAlertCeiling` live login alerts new sources fold into the `many-sources` key; `resolveQuietLoginAlerts` resolves, unmailed, any login alert whose key has no failure in the window, so the live bound is absolute and retention reclaims them; `raiseAlertTx` mails a login alert only when no login-rule delivery was created within `loginAlertCooldown`, so mail is bounded per rule, not per key), `access_removal_failed` (the expiry `*_failed` rows and `account.end_refused`), `push_fatigue` (`auth.mfa_push_fatigue`, keyed by user). Alert text is built from names via `alertText` (control characters stripped, bounded), never from `details_json`. `DeliverAlerts` mails `alert_deliveries` rows due now through the relay, re-checking `alertReaderSQL` (active, unended administrator or auditor) per message, backing off by `alertBackoff` and marking `failed` after `alertDeliveryAttempts`; `SetAlertSettings` applies the same reader check to recipients. Routes: `GET /api/admin/alerts` and `/settings` under `permRead`; acknowledge and `PUT /settings` under `permAdmin` (settings with step-up), audited as `admin.alert_acknowledged` and `admin.alerts_configured`. `EvaluateAlerts` processes at most `alertMaxBatches` batches per pass and `DeliverAlerts(ctx, …)` stops at the pass deadline; `alertWorker` runs `runAlerts` on its own goroutine every 3 seconds under `alertPassBudget` (never on the dispatch loop), with `alertSender` as the test hook. `DeleteAlertsOlderThan` (housekeeping, audit retention cutoff) trims resolved alerts and finished deliveries only.
- Upgrade and restore: migrations must be idempotent and land on the schema of a fresh install — `TestUpgradeFromPreFeatureDatabase` migrates a pre-feature database twice and compares schema fingerprints (objects, and each table's columns as a set) against a fresh one, so a migration that drops an object another migration recreates fails the build. Its legacy schema carries the KySignOn-era leftovers that `migrateLegacyPairedSystems` removes: the NOT NULL `paired_systems.hmac_secret_hash` (dropped, rows kept) and the retired `system_pairing_tokens` table (dropped; its user foreign key blocked user deletion). `kysignon restore` writes `data/restored.json`; `applyRestoreMarker` (startup, before any worker or listener) calls `ApplyRestoredState`, which queues a back-channel logout for every `oidc_client_sessions` row before the sessions are deleted (the sid mapping cascades with them, and nothing else re-derives an owed logout; already-queued sids are not duplicated and their leases are released), deletes every table in `restoredCleared` — which deliberately excludes `logout_deliveries` — closes out every undelivered `account_sync_events` row with a reason and `revision=restoredRevision` (-1) — closing alone is not enough, because `reconcileProvisioningTx` re-pends exhausted work whose revision matches current desired state and a restore unfences every row, so the sentinel is what keeps the capsule's queue from delivering when a hold lifts; stateless events (`user.deleted`, `user.mfa_reset`) still retry by design — sets `paired_systems.provisioning_hold` on every connector that is not disabled, and merges its counts into the caller's `system.restored` audit row inside the same transaction; the marker is removed only after that commits. `ClaimDueSyncEvents` skips held connectors. `releaseProvisioningHoldTx` runs from `FinishReconcileJob` only for a `repair` with `runErr == nil && report.Repaired && report.ListingError == ""` — a connector whose kind cannot be listed, a refused or truncated listing and a read-only pass all finish without an error while comparing nothing — and from `ResumeProvisioning`, the deliberate operator override for connectors that can never be listed (`POST /api/admin/systems/{id}/provisioning/resume`, `permAdmin` with step-up, `admin.provisioning_resumed`). Every connector is held by a restore, including disabled ones, so re-enabling one does not deliver capsule-era work; only the ones an operator must act on now are named in the report. Long-lived credentials the user holds (passwords, factors, recovery codes) are deliberately not cleared. The drill recipe's `required_tables` covers policy, groups, app linkage, remote mappings and job state, and `proveRestoreIsUsable` decrypts the mail relay settings as well as MFA and connector secrets.
- Explanations: `ExplainAccess(userID, appID)` reads the verdict from `effective_app_access`, the reason from the shared `accessReasonSQL` (also used by `ListAppAccessUsers`), grants with liveness from the assignment and membership rows, roles from the mappings, the policy and revisions from the app record, and the access end from `AccessEndsAt`; `account_ended` and `grants_expired` are derived in Go. The roles branch joins `app_group_assignments`, so group names appear only for groups assigned to the app. Admin route under `permAppRead`; the user route (`OwnAccessExplanation`, rate limited) returns one uniform denial (`no_access`, unknown clients included) or the allowed verdict, naming the app only when held or requestable. `denyAccess` in the OAuth handler audits denials with reason and revisions.
- Access requests: `app_registry.requestable` (admin-only `PUT …/requestable`) and `access_requests` (unique pending row per app and user, `expires_at` fourteen days out, `RunDueExpiries` flips stale ones to `expired`). `RequestableApps` lists only requestable, enabled, assigned-only apps the user lacks; `CreateAccessRequest` refuses closed or missing apps alike (`ErrAppNotRequestable`), held access, duplicates and more than `maxPendingRequests`. `DecideAccessRequest` locks the row, re-reads the actor's authority (`activeAdminSQL` or an `app_owner` delegation for the app), the requester (`ErrSelfApproval`), expiry and the app's policy, then writes the grant through `applyAppAssignmentTx`, the same function manual grants use. Inbox and decisions use `permRequests` (`anyOwner`), with `ListAccessRequests` scoping a non-admin actor to owned apps.
- Expiring access: `app_user_assignments.expires_at`, `group_memberships.expires_at` and `users.ends_at` are unix seconds (NULL = never). `app_access_facts`/`effective_app_access` and the `live_group_memberships` view apply them with `unixepoch()` on every read, so expiry needs no worker; `scanUser` reads an ended account as `disabled`; `RecordIssuedToken` checks `ends_at`; `AccessEndsAt` bounds token `exp` at exchange. `RunDueExpiries` (sync worker, at start and each minute) commits each due item in its own transaction (a failure is audited as `*_failed` and retried), runs the role and enrollment follow-ups, then one shared `revokeLostAppAccessTx` (which now also enqueues back-channel logout and drops the lost `oidc_client_sessions`) plus provisioning reconciliation, and ends accounts via `offboardUserTx`; it refuses to end the last administrator. `activeAdminSQL` is the single definition of an active administrator (role, active row, end date not passed) for every last-administrator count. `SetAppAssignmentUntil`/`SetGroupMembershipUntil` and `updateUser` refuse past instants (`ErrExpiryInPast`); `updateUser` refuses scheduling the last administrator's end; the user update handler treats an absent `endsAt` as unchanged and an empty string as a clear.
- Delegated administration: `admin_delegations` rows (`helpdesk`, `auditor`, `app_owner` with `app_id`) hand fixed permissions to ordinary users; `users.role` stays `user`/`admin` and only `admin` counts for the last-administrator invariant. Every admin route is a row in `Server.adminRoutes` naming one `permission` from `internal/api/permissions.go`; `require` computes `Access` from the users row and delegations on each request (never from the session), refuses before spending a step-up grant, and for `protectAdmins` routes refuses a non-admin actor whose target is an administrator or holds any delegation. The `administrators` enrollment scope in `applicable_enrollment_policies`/`enrollment_requirements` covers `role='admin'` or any `admin_delegations` row; `enrollment_new_delegation` derives deadlines and aborts on an unsatisfiable mask. App-owner routes are scoped to the `{id}` app; `ListAppRecords` narrows to owned apps for owners. Only global admins reach `PUT /api/admin/users/{id}/delegations`. `TestPermissionMatrixCoversEveryAdminRoute` walks the table with every actor kind and must stay in step with the README matrix.
- Users list and revoke their own live browser sessions; administrators list and revoke any user's sessions and per-app token grants. Revoking a session deletes it with its codes, tokens, step-up grants and pending authorization interactions in one transaction with the audit row; ownership is enforced in the same statement, so a foreign session ID is a no-op. Account disable and the emergency revoke button use the same complete revocation. Revocation never requires step-up. App rows come from the token registry and are not a live inventory of downstream app logins.

## WebAuthn

`internal/webauthn` is pure verification: no database, no HTTP, no CBOR. It reads the SPKI
public key and raw authenticator data the browser exports, because attestation is not
verified and re-deriving those from the attestation object would buy nothing.

KyIdentity records whether a passkey is backup-eligible but never rejects one for it. The rule
that a KyIdentity login credential must live in KyAuth's device-local `totp_vault.kdbx` rather
than the KyPasswords-synced `passwords_vault.kdbx` is enforced in KyAuth, where the vault is
chosen.

# Ponytail, lazy senior dev mode

Use the smallest correct change.

1. Reuse what already exists.
2. Prefer stdlib and native platform APIs.
3. Add dependencies only when they remove meaningful code.
4. Fix shared root causes, not one caller.
5. If a shortcut has a limit, mark it with `ponytail:` and name the upgrade path.

Non-trivial logic must include one runnable check (unit test or minimal self-check).
